# Zone Diet Application

크로스핏 레벤의 수업 예약과 회원 관리 앱입니다. 존다 참가자는 같은 계정으로 8주 식단 프로그램을 이용합니다.

온라인 데모: https://zone-diet-application.vercel.app

## 실행

Node.js 24 LTS를 사용합니다.

```sh
npm ci
npm start
```

로컬 주소는 http://localhost:3000 입니다. 로컬 개발 데이터는 `.data/`에 저장됩니다. 기존 단일 사진 기록도 그대로 사용할 수 있습니다.

## 수업 예약과 회원 등록

관리자는 **박스 회원 관리 → 회원 등록**에서 이름·아이디·초기 비밀번호를 등록합니다. 회원은 해당 계정으로 로그인하면 수업 예약 화면에 들어갑니다. 관리자는 수업별 확정 명단과 대기 순번을 확인할 수 있습니다.

| 운영 요일 | 수업 시간 |
| --- | --- |
| 월·수·금 추가 | 06:30–07:20 |
| 월~금 공통 | 09:40–10:30, 11:50–12:40, 17:30–18:20, 18:30–19:20, 19:30–20:20, 20:30–21:30, 21:30–22:20 |

예약은 한국 시간 수업 전날 00:00에 열리고, 시작 시각에 예약과 취소가 마감됩니다. 하루 한 수업을 신청할 수 있으며 대기도 포함합니다. 정규 수업은 18명까지 확정되고 다음 2명은 대기합니다. 같은 날 다른 수업에 확정 자리가 있으면 예약 화면에서 **이 시간으로 변경**을 누를 수 있습니다. 새 수업이 만석이 되면 기존 예약이나 대기 순번을 유지합니다. 두 수업 모두 시작 전이어야 합니다.

확정 회원의 취소나 시간 변경으로 자리가 나면 대기 순서대로 승격되고 해당 회원의 예약 화면에 알림이 남습니다. 회원은 기기별 알림을 켜 앱이 닫혀 있어도 웹 푸시를 받을 수 있습니다. iPhone에서는 Safari의 공유 메뉴에서 앱을 홈 화면에 추가한 뒤, 홈 화면에서 앱을 열고 알림을 허용합니다.

로그인 화면의 **아이디 찾기 · 비밀번호 재설정**에서 복구 절차를 확인할 수 있습니다. 코치는 **박스 회원 관리**에서 회원을 검색하고 본인 확인 후 아이디를 안내하거나 15분 동안 유효한 일회용 재설정 링크를 발급합니다. 재설정 후 기존 예약과 기록은 같은 회원 계정에 유지됩니다.

### 휴강과 특강

코치는 예약 화면에서 날짜를 선택하고 **코치 수업 일정 관리**를 엽니다. 주말을 포함해 수업 이름·시간·정원·대기 인원을 정한 특강을 추가할 수 있습니다. 한 수업 또는 하루 전체를 휴강할 때는 사유를 입력하고 영향을 받는 확정·대기 인원을 확인합니다. 그사이 명단이 바뀌면 최신 인원으로 다시 확인합니다.

휴강하면 해당 수업의 확정자와 대기자에게 수업 시간과 취소 안내가 전달됩니다. 당일에 하루 휴강을 설정하면 시작 전 수업만 취소합니다. 휴강을 해제하면 회원이 다시 예약할 수 있습니다.

### 회원권

코치는 **박스 회원 관리 → 이용권 관리**에서 기간권의 만료일 또는 횟수권의 잔여 횟수와 선택 만료일을 설정합니다. 회원은 예약 화면의 **내 회원권**에서 이를 확인합니다. 한국 시간으로 만료일 당일 수업까지 신청할 수 있습니다. 아직 회원권을 등록하지 않은 기존 회원은 계속 예약할 수 있습니다.

횟수권은 예약 확정 또는 대기에서 확정으로 승격될 때 1회를 차감합니다. 대기 신청은 차감하지 않고, 같은 날 확정 예약의 시간만 변경하면 추가 차감이 없습니다. 시작 전 취소나 휴강 시 해당 예약에 사용한 1회를 돌려줍니다. 코치가 기존 횟수권을 새 횟수권으로 교체한 경우에는 이전 권으로 사용한 횟수가 새 권에 합산되지 않습니다.

## 오늘의 와드

관리자는 박스 메뉴의 **오늘의 와드**에서 날짜별 운동을 게시합니다. 같은 와드를 다시 할 때 **기존 와드 불러오기**를 선택하면 회원이 예약 화면에서 이전 수행 기록과 비교할 수 있습니다. 회원은 완료 시간, 중량(kg·lb), 라운드·횟수, 스케일링을 기록하고 **내 전체 운동 기록**에서 날짜별 기록을 확인할 수 있습니다.

## 크로스핏 가이드

박스 메뉴의 **크로스핏 가이드**에서 동작, 네임드 와드, 기본 용어를 한글 이름·영문 이름·약어로 검색할 수 있습니다. 예를 들어 `토투바`, `Toes-to-Bar`, `T2B`는 같은 동작을 엽니다. 동작 설명에서 CrossFit 공식 시범 영상을 재생할 수 있습니다.

예약 화면과 **오늘의 와드**에서 가이드에 등록된 동작이나 용어를 누르면 그 자리에서 설명이 열립니다. 네임드 와드의 상세 화면에서는 운동 구성·점수 기록법과 해당 운동으로 등록된 본인의 지난 기록을 확인할 수 있습니다.

## 존다 프로그램

메뉴의 **존다 프로그램**을 누르면 기존 팀·식단·체중 기록이 열립니다. 일반 박스 회원은 관리자 화면에서 존다에 참여 등록할 수 있으며, 팀 배정은 존다 팀 관리에서 진행합니다. 기존 존다 회원은 같은 계정으로 수업 예약과 존다 기능을 모두 사용합니다.

- 관리자 팀 편성 및 식단·조장·미션운동·SNS·기타 역할 지정
- 회원별 로그인과 개인 체중·운동 기록
- 아침·점심·저녁마다 사진 최대 6장, 추가·제거 및 확대 갤러리
- 끼니별 탄수화물·단백질·지방 블록 입력 및 하루 합계 (미입력과 0 구분)
- 본인의 저장된 하루 식단으로 카페 글 제목·사진 포함 본문 생성
- 제목/본문 텍스트 복사, 사진을 내장한 HTML 파일 저장
- 네이버로 처음 로그인 → 회원의 카페 연동 동의 신청 → 관리자의 앱 회원·게시판 직접 연결
- 승인 전 신청 전용 화면, 승인 후 기존 회원 기록과 팀 이용
- 게시 대상과 사진 포함 본문을 확인한 뒤 네이버 카페에 게시 (개발자 앱 설정 필요)
- 날짜별 중복 게시 방지, 응답이 불확실한 게시 건의 관리자 확인
- 같은 팀의 식단 사진 확인
- 현재 식단 담당자만 날짜별 사진 모음을 존다 참가자 전체에게 공유
- 공유 시점의 사진 보존, 명시적인 재공유로 갱신
- 로그인·팀·역할 검사, 변경 버전 검사, 충돌 시 덮어쓰기 방지

## Vercel 배포

GitHub의 `Jung-won-seok/Zone_Diet_Application` 저장소와 Vercel의 `zone-diet-application` 프로젝트가 연결되어 있습니다. `main` 브랜치에 푸시하면 프로덕션 자동 배포가 실행됩니다. 배포 결과는 Vercel 프로젝트의 Deployments에서 확인할 수 있습니다.

`vercel.json`은 정적 화면과 Node.js API를 함께 배포합니다. 서버리스 실행 환경에서 로컬 파일 시스템에 기록을 저장하지 않습니다.

기존 Blob 방식으로 시작할 때는 다음과 같이 설정합니다. PostgreSQL로 전환하는 순서는 아래에 있습니다.

1. Vercel 프로젝트에 **Private Vercel Blob** 저장소를 연결합니다.
2. `BLOB_READ_WRITE_TOKEN`과 `INITIAL_ACCOUNT_PASSWORDS`를 Production 환경변수에 설정합니다. `.env.example`에서 키 형식을 확인할 수 있습니다.
3. 새 박스는 `INITIAL_ACCOUNT_PASSWORDS`에 `admin`의 8자 이상 비밀번호를 담은 JSON을 설정하고 첫 로그인 후 실제 회원을 등록합니다. 기존 데모 구성은 `admin`과 `member01`부터 `member20`까지의 초기 비밀번호를 모두 지정하면 생성됩니다.
4. 이 설정은 빈 저장소의 첫 초기화에만 적용됩니다. 기존 저장소를 연결하면 회원·팀·식단과 네이버 연결을 그대로 사용합니다.

기존 방식은 비공개 Blob에 사진과 앱 데이터를 저장하며 ETag로 동시 쓰기를 검사합니다. PostgreSQL 모드에서는 사진 원본만 같은 비공개 Blob에 보관합니다. 두 방식 모두 사진을 열 때 로그인과 공개 범위를 확인합니다.

### PostgreSQL 연결과 기존 데이터 이관

박스 전용 PostgreSQL 또는 Supabase 프로젝트를 준비합니다. Supabase에서는 프로젝트의 **Connect**에서 서버리스용 트랜잭션 풀러 연결 주소를 복사합니다. 이관 도구와 서버는 비공개 `leben` 스키마를 사용합니다. 최초 설치와 앱 실행에는 해당 스키마와 테이블을 소유하는 서버 계정을 사용합니다. 연결 주소는 개발 시 `.env.local`, 배포 시 Vercel의 서버 환경변수 `LEBEN_DATABASE_URL`에 설정합니다. 원격 DB는 인증서를 검증합니다. 전용 CA가 필요한 경우 `LEBEN_DATABASE_CA`에 프로젝트의 CA 인증서를 설정합니다.

예약 순서, 수업 정원, 회원권과 사용 이력은 별도 테이블에 저장합니다. 기본 주간 시간표는 앱의 기존 규칙을 사용하고, 예약이나 휴강·특강 설정이 생기면 해당 날짜의 수업을 DB에 기록합니다. 예약 변경과 횟수 차감·복구가 한 트랜잭션에서 확정됩니다. 기존 계정과 세션, WOD·식단 기록, 알림, 사진 참조도 함께 이관합니다. 횟수권 변경 이력의 시작 값은 이관 시점의 잔여 횟수입니다.

**시험 이관**

운영과 분리된 빈 DB에 연결하고, 기존 비공개 Blob의 `BLOB_READ_WRITE_TOKEN`을 이관 환경에 설정합니다. 백업에는 계정과 세션이 포함되므로 접근이 제한된 폴더에 저장합니다. 아래 예시는 PowerShell에서 실행합니다.

```powershell
New-Item -ItemType Directory -Force .data/migration | Out-Null
npm run db -- backup .data/migration/trial.json
npm run db -- schema
npm run db -- dry-run .data/migration/trial.json
npm run db -- import .data/migration/trial.json
npm run db -- verify .data/migration/trial.json
```

`schema`는 새 스키마를 한 번 설치합니다. `dry-run`은 실제 제약 조건과 재조회 결과를 확인한 뒤 되돌립니다. `import`는 빈 대상에서만 실행되며, 원본의 대기 순서와 회원별 잔여 횟수를 포함해 모든 필드가 일치해야 커밋합니다. `verify`는 현재 DB를 백업과 다시 대조합니다. 원본이 로컬 파일이면 첫 명령 대신 `npm run db -- backup-local .data/store.json .data/migration/trial.json`을 사용합니다. 사진 원본은 이 백업에 포함되지 않으므로 기존 비공개 Blob을 유지하고 사진 파일도 별도로 백업합니다.

로컬에서는 시험 DB를 가리킨 상태로 `LEBEN_STORE=postgres`를 설정한 뒤 `npm start`로 로그인과 예약을 확인합니다. 운영 Blob과 연결된 상태에서 사진 쓰기·삭제를 시험하면 운영 사진에 영향을 줄 수 있으므로 사진 시험에는 별도의 Blob이나 로컬 사진 폴더를 사용합니다. 로컬 실행에서 Blob 토큰을 비우면 사진은 `.data/media/`를 사용합니다.

**운영 전환**

1. 새 코드를 먼저 기존 저장 방식으로 배포하고, 점검 전에 레벤 전용 운영 DB에 `schema`를 한 번 실행합니다. 시험 데이터를 넣었던 DB는 시험용으로 유지합니다.
2. 기존 운영 도메인에 `LEBEN_MAINTENANCE=1`을 적용해 재배포합니다. API에서 503을 확인하고, 이전 배포 주소와 쓰기 작업도 차단한 뒤 진행 중인 요청이 끝날 때까지 기다립니다.
3. `backup .data/migration/final.json`으로 최종 백업을 새로 만듭니다. 운영 DB를 대상으로 `dry-run`, `import`, `verify`를 같은 파일에 순서대로 실행합니다. 전체 대조를 마친 뒤에 서비스를 엽니다.
4. Vercel Production에 검증한 `LEBEN_DATABASE_URL`과 `LEBEN_STORE=postgres`를 설정하고 점검 설정을 해제해 재배포합니다. 기존 Blob 토큰과 네이버 암호화 키는 유지합니다. 코치·회원 로그인을 확인하고 테스트 회원으로 예약·취소 시 명단과 잔여 횟수를 확인합니다.
5. 새 DB에서 첫 쓰기가 발생하기 전까지는 점검 상태에서 기존 Blob 방식으로 되돌릴 수 있습니다. 이후에는 다시 쓰기를 중지하고 PostgreSQL의 최신 변경을 복구에 포함해야 합니다. 운영 DB 자체의 정기 백업과 복원 시험도 설정합니다.

동시 예약 통합 테스트는 임시 DB를 생성할 수 있는 테스트 계정으로 `LEBEN_TEST_DATABASE_URL`을 설정한 뒤 `npm test`로 실행합니다. 테스트가 직접 생성한 임시 DB만 정리합니다. GitHub의 풀 리퀘스트와 `main` 푸시에서는 별도 PostgreSQL 17 컨테이너로 이 테스트를 실행하도록 설정했습니다.

## 네이버 카페 연결 설정

네이버 개발자 앱의 키가 없으면 설정 화면과 미리보기는 사용할 수 있지만 실제 계정 연결과 게시는 비활성화됩니다. 기본 카페는 `https://cafe.naver.com/mycaffelatte` (카페 ID `31811778`)입니다. 예시 게시판 ID `7`은 특정 회원에게 자동 배정하지 않습니다.

1. [네이버 개발자 센터](https://developers.naver.com/apps/#/register)에서 애플리케이션을 등록하고 사용 API에서 **카페**를 추가합니다. 자동으로 추가되는 **네이버 로그인**과 카페 API 권한을 확인합니다. 표시용 별명/이름은 선택 동의 항목으로 사용할 수 있습니다. 회원 식별에는 이름이 아닌 네이버 고유 식별자를 사용합니다.
2. 웹 서비스 URL은 `https://zone-diet-application.vercel.app`, Callback URL은 `https://zone-diet-application.vercel.app/api/naver/callback`으로 등록합니다.
3. Vercel 프로젝트 Settings → Environment Variables의 Production에 다음 값을 설정한 뒤 재배포합니다. Secret과 암호화 키를 GitHub, 브라우저 코드, 채팅에 넣지 마세요.

| 환경변수 | 값 |
| --- | --- |
| `NAVER_CLIENT_ID` | 네이버 개발자 앱의 Client ID |
| `NAVER_CLIENT_SECRET` | 같은 앱의 Client Secret |
| `NAVER_CALLBACK_URL` | 위 Production Callback URL |
| `NAVER_TOKEN_ENCRYPTION_KEY` | 무작위 32바이트를 Base64로 인코딩한 값 |

암호화 키는 서버에 저장하는 네이버 토큰 보호용입니다. 비밀번호 관리자 등에서 안전하게 보관하고 연결된 계정이 있는 동안 변경하지 마세요. 키를 변경하면 기존 회원의 재연결이 필요합니다. 키는 `node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64'))"`로 생성할 수 있습니다.

로컬에서는 기존 `.env.local`에 위 네 가지 설정을 추가합니다. 로컬 Callback URL은 `http://localhost:3000/api/naver/callback`이고 네이버 개발자 센터에도 따로 등록해야 합니다. `npm start`가 `.env.local`을 읽습니다. 기존 파일에 있는 다른 설정을 지우거나 운영 환경변수 전체를 로컬로 복사하지 마세요.

개발 중에는 개발자 센터의 테스트 ID를 등록하여 이용하고, 실제 회원 대상 운영 전에 [네이버 로그인 검수 안내](https://developers.naver.com/docs/login/verify/verify.md)를 확인하세요. 해당 회원은 카페 가입과 대상 게시판의 글쓰기 권한을 갖고 있어야 합니다. API 계약은 [공식 카페 API 문서](https://developers.naver.com/docs/login/cafe-api/cafe-api.md)를 따릅니다.

### 실제 이용 순서

1. 네이버로 연결하려는 회원은 **존다 참가자 네이버 로그인**을 펼쳐 네이버로 로그인합니다. 처음 연결하는 계정은 신청 화면으로 이동하고, 이미 승인된 계정은 수업 예약 화면으로 이동합니다. 관리자가 등록한 박스 아이디는 첫 화면의 회원 로그인 폼을 사용합니다.
2. **카페와 연동하시겠습니까?**에서 이름·카페 닉네임·희망 게시판을 입력하고 동의한 뒤 **관리자에게 연결 요청**을 누릅니다. **나중에**를 선택하면 요청이 전송되지 않습니다. 네이버 인증 이름과 카페 닉네임은 다를 수 있으며, 입력한 카페 닉네임 자체를 인증된 정보로 취급하지 않습니다.
3. 관리자는 **네이버 카페 연결 → 연결 신청**에서 인증된 네이버 표시 이름과 신청 내용을 보고 앱 회원 계정(`member01` 등) 및 개인 게시판을 직접 선택합니다. 앱 회원 이름도 실제 이름으로 수정할 수 있습니다. 게시판 링크를 붙여 넣으면 ID를 추출할 수 있습니다. 이름이 같아도 자동으로 연결하지 않으며, 승인하면 선택한 기존 회원 계정의 기록·팀·역할이 해당 네이버 사용자에게 배정됩니다.
4. 회원이 신청 상태를 새로고침하면 승인된 회원 화면으로 들어갑니다. 이후 같은 네이버 계정으로 로그인하면 바로 해당 회원으로 이용합니다. 반려 사유가 있으면 확인 후 다시 신청할 수 있습니다. 카페 자체의 가입·등급·글쓰기 권한은 네이버 카페에서 별도로 갖춰야 합니다.
5. 아침·점심·저녁 사진과 탄·단·지 블록을 저장한 뒤 **네이버 카페에 올리기**를 누릅니다. 프로그램 시작일을 기준으로 만든 `5.10일 존다 20일차` 형식의 제목, 사진, 하루 합계와 게시 대상을 확인한 뒤 게시합니다. 기본 공개 설정은 카페 회원 공개, 검색 비공개입니다.
6. 성공하면 게시글 링크를 저장합니다. 같은 프로그램·회원·날짜는 다시 게시하지 않습니다. 게시 후 수정은 카페에서 처리합니다.

같은 네이버 계정으로 다시 로그인할 때는 기존 승인을 유지합니다. 연결을 해제하고 계정을 새로 연결할 때는 관리자 승인이 다시 필요합니다. 네이버 비밀번호는 앱에서 입력받거나 저장하지 않습니다. 토큰은 서버에서 암호화해 보관하며 다른 회원이나 관리자에게 반환하지 않습니다. 연동 요청 알림은 앱의 관리자 요청 목록에서 확인합니다.

네이버 응답이 끊기거나 결과 저장에 실패하면 중복 글을 막기 위해 자동 재시도하지 않습니다. 관리자가 실제 카페를 확인한 뒤 게시글 주소를 등록하거나, 글이 없는 것을 확인하여 재시도를 허용할 수 있습니다. 진행 중인 요청은 최소 2분이 지나야 수동 처리할 수 있습니다. 외부 인증/게시 계약은 모의 응답으로 검증했으며, 실제 키와 카페 권한을 설정한 후 실계정 확인이 필요합니다.
